# Capable-model action authorization follow-up

## Reason for the follow-up

The first frozen screen used the two small model families from the earlier
attention studies. Qwen2.5-0.5B-Instruct and SmolLM2-1.7B-Instruct each produced
zero executable clean actions out of 24 tasks. Their poisoned prompts sometimes
produced exact attacker actions, but none were eligible because the paired clean
task failed. The detector therefore could not be evaluated.

This is a model-capability failure, not evidence for or against the provenance
graph. The original observations remain published with null policies and failed
advancement decisions.

## Clean-only selection

Model selection observes only the 24 clean prompts generated by the frozen
protocol at commit `6dbf782a7a7b573d19cfb17c6ceb4854a128325c`. It does not
load poisoned or benign-control prompts, fit a detector threshold, or inspect a
spectral score. `screen_action_capability.py` requires the unchanged exact
three-string-field JSON envelope.

Two different model families cleared the 90% capability floor:

| Model | Backend | Immutable revision | Exact clean actions |
| --- | --- | --- | ---: |
| `mlx-community/Qwen3-4B-Instruct-2507-4bit` | MLX | `50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b` | 24/24 |
| `google/gemma-4-E2B-it` | Transformers | `70af34e20bd4b7a91f0de6b22675850c43922a03` | 24/24 |

The checked-in capability records retain every clean response, prompt and token
hashes, runtime versions, model metadata, and source hashes. Their SHA-256
digests are recorded in `selection.json`.

## Frozen follow-up

The follow-up keeps the original action schema, renderer, source registry,
host-owned source links, graph construction, score directions, simple baselines,
development splits, grading, calibration ceiling, and advancement gate. The only
runtime addition is deterministic MLX generation for the selected quantized Qwen
checkpoint. Gemma uses the existing deterministic Transformers runtime.

Materialize token-matched corpora independently for each selected tokenizer.
Run each model sequentially. Fit thresholds on `development_fit`, save the policy,
and only then generate `development_check`. Do not change the parser or recover
JSON from Markdown, XML, YAML, or prose. Never execute a proposed action.

This remains a development screen. The clean prompts were observed for model
selection, attack templates are synthetic, and related task templates span both
development partitions. Passing can justify a fresh study; it cannot support a
deployment claim.
